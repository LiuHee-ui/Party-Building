# 04 · 审核依赖倒置与认证链路

> 对应代码：`party-audit`（AuditService / AuditableHandler）、`party-auth`（AuthService /
> AdminApplyService / 两个审核处理器 / WechatMiniappClient）
> 状态：✅ 完成，**party-audit 11 个测试 + party-auth 25 个测试全通过**，编译 BUILD SUCCESS

---

## 一、这个模块解决什么问题

审核看起来简单——「待审核 → 通过 / 驳回」。但它有一个绕人的结构性难题：

**审核流水要集中，审核动作要分散。**

- 流水必须集中：一颗操作日志表，能回答「谁在什么时候改了这条数据的状态」，
  这是 spec 里「审核可追溯」的硬要求。
- 动作必须分散：被审对象分布在不同模块的表上——资源在 `t_resource`、实名在 `t_user`、
  管理员申请在 `t_admin_application`，以后还有评论在 `t_comment`。

如果让审核模块去 `UPDATE` 所有这些表，它就要依赖所有业务模块 → 依赖成环，
而且**每加一种可审对象都得改审核模块**。

**一句话**：审核这个需求逼着你把「集中」和「分散」这对矛盾解决掉，而解法就是依赖倒置。

---

## 二、涉及的工程能力

| 能力 | 具体内容 |
|---|---|
| 依赖倒置（DIP） | 能力接口定义在消费者侧、实现由提供者注册 |
| Spring 装配 | 集合注入 `List<Bean>`、`ObjectProvider` 可选依赖、启动期一致性校验 |
| 状态机与并发 | 用 SQL 条件 + 影响行数保证状态迁移的并发安全 |
| 缓存与登录态 | Token 签发、ThreadLocal 上下文、TTL 语义 |
| 密码学应用 | 随机 IV 加密 vs 确定性哈希的分工 |
| 越权防护 | 数据范围为空集时必须生成恒假条件 |
| 外部接口集成 | 微信 API 的错误处理（HTTP 200 也可能是错误） |

## 三、关键决策与取舍

### 决策 1：审核状态迁移用依赖倒置，而不是反向依赖

**选择**：`party-audit` 定义能力接口，业务模块实现并注册。

```java
// party-audit 定义
public interface AuditableHandler {
    AuditBizType bizType();
    void migrate(long bizId, AuditAction action, String remark, long operatorId);
}

// party-auth 实现（同样是 party-content、party-interact 的模式）
@Component
public class RealNameAuditHandler implements AuditableHandler { ... }
```

`AuditServiceImpl` 构造时注入 `List<AuditableHandler>`，按 `bizType` 建注册表。

**被否决**：让 `party-audit` 直接依赖各业务模块去改状态。
→ 成环，且每新增一种可审对象都要改 audit。

**收益（三条，都很实在）**：
1. 依赖图是 DAG，`party-audit` 只依赖 `common`
2. 新增可审对象时，**audit 模块零改动**——只需新增一个 Handler 实现类
3. 待审队列只查自己的流水表，**不需要访问任何业务表**（下面细说）

**一个必要的签名调整**：`migrate` 最初没有 `operatorId` 参数，但管理员申请要落 `reviewer_id`。
有两种拿法——从 `LoginContext` 取，或显式传参。
**我选了显式传参**：处理器不依赖请求上下文，单测里可以直接调，不用伪造 ThreadLocal。
> 这是个小决定，但值得记住：**能显式传的依赖，不要藏在上下文里。**

### 决策 2：待审队列不查询业务表

`t_audit_log` 上有一个 `pending` 字段：`SUBMIT` 时置 1，`APPROVE`/`REJECT`/`TAKE_DOWN` 时置 0。

于是待审队列就是：

```sql
SELECT * FROM t_audit_log WHERE pending = 1 AND org_id IN (可见组织)
```

**为什么不用 `action != 'APPROVE'` 之类的条件**：那种条件走不了索引。
把最高频查询的条件**显式建模成字段**，查询就退化为纯索引扫描。

**这条设计的连带好处**：待审队列不需要 JOIN 任何业务表，
所以 `party-audit` 真的可以只依赖 `common`。**架构上的解耦是靠数据模型配合的，
不是只靠接口定义。**

---

### 决策 3：状态迁移的并发安全靠 SQL 条件，不靠「先查后判」

```sql
UPDATE t_user SET audit_status = #{toStatus}, audit_remark = #{remark}
 WHERE id = #{userId} AND audit_status = 0 AND deleted = 0
```

```java
int rows = userMapper.migrateAuditStatus(bizId, toStatus, remark);
if (rows == 0) {
    throw new BizException(ErrorCode.AUDIT_ILLEGAL_TRANSITION, "该申请不处于待审核状态");
}
```

**为什么不能在 Java 里判断**：

```
线程 A: 查状态 → 待审核 ✓
线程 B: 查状态 → 待审核 ✓
线程 A: UPDATE ... → 通过
线程 B: UPDATE ... → 驳回        ← 状态被改坏了
```

**把状态条件写进 WHERE，让数据库来判定**：`audit_status = 0` 这个条件使第二次 UPDATE
影响 0 行，代码识别到 0 行就抛 4004。**数据库的行锁保证了这一步的原子性。**

同一模式也用在了 `t_admin_application` 的 `migrateStatus` 上。

> **可迁移的原则**：涉及状态迁移的写操作，把「前提条件」写进 WHERE，
> 用影响行数判断是否成功。这是最简单的乐观并发控制。

### 决策 4：手机号查重不能用密文——随机 IV 带来的真实陷阱

这是本次开发中**最有价值的一个发现**。

**问题**：实名提交时要校验「手机号是否已被占用」，直觉写法是：

```java
WHERE mobile_cipher = encrypt(手机号)   // ❌ 永远查不到
```

**为什么失效**：GCM 每次加密用**随机 IV**，同一手机号两次加密得到的密文**完全不同**。
等值查询永远匹配不上——这个校验等于没写，而且**不会报错，只会静默失效**。

**解法**：加一个确定性哈希列，唯一索引。

```sql
`mobile_hash` VARCHAR(64)   -- HMAC-SHA256
UNIQUE KEY `uk_mobile_hash` (`mobile_hash`)
```

三个字段各司其职：

| 字段 | 用途 | 是否解密 |
|---|---|---|
| `mobile_cipher` | 需要完整号码时读取 | 是（触发敏感访问日志） |
| `mobile_hash` | 唯一性校验 | 否 |
| `mobile_tail` | 列表展示 | 否 |

**为什么用 HMAC 而不是裸 SHA-256**：手机号只有 11 位，枚举空间约 10¹¹，
**裸 SHA-256 可以被彩虹表或暴力枚举反推**。用密钥做盐后，拿到数据库也无法离线枚举。

> **这个坑值得记牢**：加密和哈希解决的是不同问题。
> **加密用于「存下来以后要还原」，哈希用于「只做比对」**。
> 一旦给加密引入了随机性（这本身是好事），它就不能再用于等值查询了。

### 决策 5：「未提交」和「待审核」必须区分

`t_user.audit_status` 用四个值：

```
9 = 未提交实名    ← 建档默认值
0 = 待审核
1 = 已通过
2 = 已驳回
```

**如果混用会怎样**：建档默认 0（待审核），那么一个刚登录、什么都没填的用户，
会**出现在管理员的待审队列里**——管理端点开发现没内容，待办数字也是虚的。

**这条设计的本质**：**状态机要把「没开始」和「进行中」分开**。
只有「未提交」的用户才该被前端引导去填表；已经提交待审核的用户被反复引导填表是糟糕的体验。

### 决策 6：越权防护——空集不能退化成全集

```java
private void applyDataScope(LambdaQueryWrapper<AuditLog> wrapper) {
    List<Long> visible = LoginContext.currentVisibleOrgIds();
    if (visible == null) return;              // null = 不限范围（平台管理员）
    if (visible.isEmpty()) {                  // 空集 = 无任何可见组织
        wrapper.eq(AuditLog::getId, -1L);     // ← 必须生成恒假条件
        return;
    }
    wrapper.in(AuditLog::getOrgId, visible);
}
```

**为什么空集要特判**：如果直接 `if (!visible.isEmpty()) wrapper.in(...)`，
那么「可见组织为空」就等于**不加任何组织条件** → 查询退化成全表 → **越权看到所有组织的数据**。

这是数据权限里最典型的漏洞，**而且测试很难发现**——因为它只在「用户不属于任何组织」
这种边界情况下触发。所以我在测试里专门写了一条：`emptyVisibleOrgsReturnsNothing`。

### 决策 7：可选依赖 + 降级不提权

管理员申请通过后要授予角色，授予哪一类取决于组织层级：
党委（level=1）→ 上级组织管理员，党总支/党支部 → 组织管理员。

但**组织层级在 `party-org`，而 `party-org` 依赖 `party-auth`**——直接依赖又是环。

**解法**：把「查组织层级」抽成接口放 `common`（双方共同的下层），由 `party-org` 实现。

```java
public interface OrgLevelProvider {   // party-common 定义
    int levelOf(long orgId);
}
```

`party-auth` 用 `ObjectProvider<OrgLevelProvider>` **可选注入**：

```java
OrgLevelProvider provider = orgLevelProvider.getIfAvailable();
if (provider == null) {
    return RoleType.ORG_ADMIN;   // 降级到最低管理权限，而不是提权
}
```

**两个要点**：
1. **可选注入**让 `party-auth` 在 `party-org` 尚未就位时也能独立编译与运行——
   这对按模块推进的项目很实用。
2. **降级方向必须是「更小的权限」**。如果降级逻辑写成「查不到就给最高权限」，
   那就是一个权限提升漏洞。测试里专门验证了这一点。

### 决策 8：微信接口「HTTP 200 也可能返回错误」

```java
int errcode = body.path("errcode").asInt(0);
if (errcode != 0) throw new BizException(ErrorCode.WECHAT_CODE_INVALID);
```

微信的接口即使业务失败也返回 HTTP 200，错误信息在 body 的 `errcode` 里。
**只看 HTTP 状态码会把「code 无效」当成登录成功**，然后拿着一个空 openid 继续往下走。

同时：异常统一归到 `2002 凭证无效`，**不把微信的原始报错透给客户端**——
外部系统的错误信息不该出现在自己的 API 契约里。

## 四、可迁移的方法论

1. **集中与分散的矛盾，用依赖倒置解**：消费者定义接口，提供者实现。
2. **把最高频查询的条件显式建模成字段**，让它能被索引。
3. **状态迁移把前提条件写进 WHERE，用影响行数判断结果**。
4. **加密和哈希分工明确**：要还原用加密，只比对用哈希。引入随机 IV 后就不能等值查询。
5. **状态机区分「未开始」和「进行中」**，否则待办列表会出现幽灵数据。
6. **数据范围为空的判断，永远要单独处理**，不能让它退化成「不加条件」。
7. **降级策略的方向必须指向更小的权限。**

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 什么是依赖倒置？和依赖注入什么关系？ | DIP 是原则（高层不依赖低层，都依赖抽象）；DI 是实现手段（由容器注入）。**有了 DI 不等于符合 DIP** |
| 2 | 循环依赖怎么打破？ | ① 提取公共依赖到下层 ② 依赖倒置（定义接口由上层实现）③ 事件解耦。**本项目用了两次第 ② 种** |
| 3 | Spring 循环依赖能自动解决吗？ | 只能解决**单例 + setter/字段注入**的循环；构造器注入的循环直接启动失败。而且这只是「不让它报错」，不是好设计 |
| 4 | 怎么保证状态机迁移的并发安全？ | 把前提状态写进 UPDATE 的 WHERE，判断影响行数；或用乐观锁版本号。**不要先查后改** |
| 5 | 为什么同一明文两次加密结果不同？ | 用了随机 IV。**这是特性不是 bug**，IV 复用会导致 GCM 彻底失效 |
| 6 | 加了随机 IV 后怎么做唯一性校验？ | 另存确定性哈希列 + 唯一索引。**不能对密文做等值查询** |
| 7 | 手机号哈希为什么不能直接用 SHA-256？ | 枚举空间小（10¹¹），可被彩虹表反推。要用 HMAC 或加盐 |
| 8 | ThreadLocal 在线程池里有什么坑？ | 线程复用导致数据串号；必须 `remove()`。**权限上下文尤其危险** |
| 9 | 数据权限做错了会怎样？举一个典型漏洞 | 「可见范围为空」时忘记特判 → 查询退化成不带条件 → 越权看到全部数据 |
| 10 | 调外部接口最容易被忽略什么？ | ① HTTP 200 但业务失败 ② 超时设置 ③ 把对方原始报错透给自己的客户端 |
| 11 | `ObjectProvider` 和直接 `@Autowired` 有什么区别？ | 前者允许 Bean 不存在（可选依赖），支持延迟获取。**适合跨模块的可选能力** |
| 12 | 为什么审核状态不用布尔字段？ | 布尔无法表达「未提交 / 待审核 / 通过 / 驳回」四态，也无法追溯。**状态数超过 2 个就该用状态机** |

## 六、可延伸的数据/算法点

- **审核流水是一张天然的「事件表」**。它记录了每条业务对象的状态变迁轨迹与时间戳，
  可以直接拿来做**流程时长分析**（提交到审核通过的耗时分布），
  发现「哪些组织/哪些类型的审核积压最严重」。这是运营分析里很常见的题目。
- **依赖图的拓扑排序**在 01 篇提过一次，这里是第二个应用场景：
  如果依赖关系是运行期通过 Bean 注册形成的，可以写一个启动自检，
  解析所有 `AuditableHandler` 的 `bizType` 并检测重复注册——
  项目里已经这么做了（重复注册会让启动直接失败）。
  这类「用图算法换取启动期安全」的思路，比单纯刷题更有工程价值。

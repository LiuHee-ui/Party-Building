# 07 · 答题判分与排行榜

> 对应代码：`party-exam`（ExamJudge / PaperQuestion / PeriodRange / RankingKey /
> ExamService / RankingService / DashboardService / RankingSnapshotJob）
> 状态：✅ 完成，module 内 34 个测试通过

---

## 一、这个模块解决什么问题

两件事：**判分**和**排名**。它们有一个共同点——**结果的权威性完全依赖服务端**。

- 判分：客户端可以改分数、改答案、改提交次数
- 排名：客户端可以伪造分值、伪造名次

所以这两个功能的正确性不是"算得对"，而是**算的地方对**。

**一句话**：凡是结果会影响评价的功能，计算必须发生在用户碰不到的那一侧。

## 三、关键决策与取舍

### 决策 1：客户端只提交「选了哪些选项」

```java
// 请求体：题目 id → 选中选项
Map<Long, List<String>> answers
```

**被否决**：客户端提交 `score` 或提交「对了哪几题」。

**为什么**：任何由客户端计算并回传的结果，都等于把评分权交给了客户端。
提交选项后，答案比对、分值加权、是否及格全在服务端算。

**配套的关键约束**：**标准答案不能出现在任何面向客户端的返回体里。**
试卷接口 `getPaperForUser` 只装配题干与选项，`correctOptions` 字段根本不在 VO 里——
不是「记得过滤掉」，而是**类型系统上就不存在**。

> 这比"记得别传"可靠得多。**能靠类型保证的，不要靠代码规范保证。**

---

### 决策 2：多选题不给部分分

```java
private static boolean matches(List<String> selected, Set<String> correct) {
    return new HashSet<>(selected).equals(new HashSet<>(correct));
}
```

**为什么不做部分给分**：这是党建知识考核，规则要**能被向党员解释清楚**。
「多选题少选错选都算错」一句话说完；如果做部分给分，就得解释
「选对 2 个给 50%」「多选一个扣 25%」这套加权规则——既难解释，也更容易被钻空子。

**顺带的好处**：判定逻辑就是集合相等，不需要维护加权表，也不会有浮点误差。

> 取舍点：**可解释性也是一种正确性。** 规则复杂到用户无法预期结果时，
> 系统就算"算得对"，用户也不信。

---

### 决策 3：排行榜按组织分片

```
rank:1:learn:2:2026-09:3    → 组织 3 的本月学时个人榜
```

**被否决**：一张全国总榜 `rank:learn:2026-09`。

**为什么分片**：
1. **越权隔离**：用户端只会看「本组织榜单」。分片后按登录态取键，
   **天然不可能读到别的组织**——不需要额外的权限判断
2. **分片大小可控**：一个党支部几十到几百人，ZSET 操作始终是小常数
3. **管理端另有通道**：跨组织榜读快照表，不查 Redis

> **把权限设计进数据结构，而不是设计进查询条件。** 这是本篇最值得记住的一条。

**键里带 periodKey 而不是靠 TTL 过期**：过期时间不够精确，
会让「本月榜」在某天突然消失。显式带周期标识更可控，TTL 只做内存回收兜底。

---

### 决策 4：ZSET 是排行榜的正确答案，但有两个坑

用 `ZADD / ZINCRBY / ZREVRANGE / ZREVRANK` 拿到 O(log N) 的写入与排名查询，
这是 ZSET 的经典用法。两个坑必须记住：

**坑一：`ZREVRANK` 返回的是 0 起下标。**

```java
Long zeroBased = redis.opsForZSet().reverseRank(key, member);
return zeroBased == null ? null : zeroBased + 1;   // 对外统一 1 起
```

**坑二：名次不存在时返回 null，不能返回 0。**

```java
return zeroBased == null ? null : zeroBased + 1;
```

如果返回 0，前端会显示「第 0 名」。测试里专门验了这条：
`rankOfAbsentReturnsNull`。

**坑三（本题遇到的 Mockito 坑）**：`any()` 用在 `int` 参数上会拆箱成 null 并抛 NPE，
应该用 `anyInt()`。而且这个 NPE 会**污染后续测试**——
Mockito 的参数匹配器栈是线程级的，一次异常没清理会让下一个测试报
`InvalidUseOfMatchers`，看起来像另一个测试坏了。

---

### 决策 5：实时写入 + 每日重算，两条路径都要有

```
实时路径：学时入账 → RankingScoreProvider（SPI）→ ZINCRBY
重算路径：每日 02:00 → 从数据库重算 → 覆盖 Redis + 落快照表
```

**为什么不能只有实时路径**：Redis 会抖动、会丢数据。榜单一旦错乱，
用户看到的名次就是错的，而**这种错误没有自愈能力**。

**为什么不能只有重算路径**：榜单一天不更新，用户学完看不到自己名次变化，
激励效果直接没了。

**两条路径的分工很清晰**：实时路径负责"快"，重算路径负责"对"。
重算是**全量覆盖**而不是增量补齐，所以它能自动修复任何丢失与错乱。

**快照任务的幂等**：先 `delete` 同 (scope, periodType, periodKey, snapshotDate)
的旧数据再插入。任务重跑、补跑都不会产生重复名次。

**并发读取的细节**：管理端查询先取 `MAX(snapshot_date)` 再按该日期读全量，
避免读到任务执行中途的「半份」数据。

### 决策 6：第三处依赖倒置

学时产生在 `party-learn`，榜单实现在 `party-exam`，而 `party-exam` 依赖 `party-learn`
（方向不能反过来）。如果让 learn 直接调 exam 就成环了。

解法还是 SPI：`common/spi/RankingScoreProvider` 由 exam 实现，learn 用
`ObjectProvider` 可选注入。

**这次多了一个细节**：实现类里**吞掉了 Redis 异常**。

```java
try {
    rankingService.increaseScore(...);
} catch (Exception e) {
    log.error("学时榜单写入失败，将由快照任务兜底", e);
}
```

**为什么敢吞**：榜单是增值功能，学时入账是核心功能。
如果榜单写失败导致心跳接口报错，用户会以为「学习记录丢了」——
**用一个次要功能的故障去影响主流程，是典型的兜底设计错误。**

> 判断标准很简单：**这个故障会不会让用户无法完成核心动作？**
> 会，就必须抛；不会，就该降级 + 告警 + 兜底。

---

### 决策 7：看板指标的「分母」必须写在文档里

五项指标里最容易出问题的是两个比例：

| 指标 | 分子 | 分母 |
|---|---|---|
| 活跃度 | 区间内有有效学习的人数 | **在册人数** |
| 达标率 | 累计学时 ≥ 目标的人数 | **有学时记录的人数** |

两个分母**故意不同**。活跃度衡量"全体动员程度"，分母应该是在册人数；
达标率衡量"学了的人里面有多少达标"，分母应该是有学习记录的人。

**如果混用会怎样**：数字看起来接近，但含义完全不同，且各人算出不一样。
这类问题不会报错，只会让人"觉得数据不太对"——**最终结果是没人信看板**。

所以我把口径直接写进了 `DashboardVO` 的类注释里，代码改了注释就必须跟着改。

---

### 决策 8：分布桶要补齐零值

```java
for (Map.Entry<String, String> entry : BUCKET_LABELS.entrySet()) {
    bucket.setCount(counts.getOrDefault(entry.getKey(), 0L));
}
```

SQL 的 `GROUP BY` 只会返回**有数据的桶**。如果某一段没人，
直接返回会导致前端画图缺柱子、比例算错。

所以桶的顺序与文案固定在 Java 侧（`BUCKET_LABELS`），SQL 只负责填数——
**让前端拿到的一定是完整的五段**，而不是"有几个返回几个"。

## 四、可迁移的方法论

1. **结果影响评价的功能，计算必须在服务端**；能靠类型消除的字段，不要靠过滤。
2. **把权限设计进数据结构**（键的分片），而不是设计进查询条件。
3. **排名类返回值要区分「不在榜」和「第 0 名」**，用 null 表达缺失。
4. **缓存 + 定时重算两条路径都要有**：一个管快，一个管对。
5. **定时任务的幂等靠"先删后插"**，而不是"判断已存在就跳过"。
6. **次要功能的故障不该影响主流程**：降级 + 告警 + 兜底重算。
7. **多指标看板把每个分母写进文档**，否则数字会"看着差不多但没人信"。

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 排行榜为什么用 Redis ZSET 而不是 MySQL `ORDER BY`？ | ZSET 的 `ZADD`/`ZINCRBY`/`ZREVRANGE` 都是 O(log N)，且**天然有序**；MySQL 每次都要排序，数据量大时成为瓶颈 |
| 2 | ZSET 的底层实现是什么？ | 跳表 + 哈希表。跳表支持范围查询与排名，哈希表提供 O(1) 的分数查找 |
| 3 | ZSET 的排名 API 有什么坑？ | `ZRANK`/`ZREVRANK` 返回 **0 起下标**；成员不存在返回 nil，要转成业务上的"未上榜" |
| 4 | 排行榜要不要分片？怎么分？ | 看访问模式。只看本组织就按组织分片，天然隔离权限且分片大小可控；要看全局就用快照表或全局榜 |
| 5 | 缓存与数据库不一致怎么处理？ | 两条路径配合：实时写缓存保证体验，定时全量重算保证正确。**重算要全量覆盖，不能增量补齐** |
| 6 | 定时任务怎么保证幂等？ | 以业务唯一键为目标做"先删后插"，或用唯一约束 + `ON DUPLICATE KEY UPDATE` |
| 7 | 怎么防止客户端篡改判分结果？ | 判分在服务端；答案不下发；提交的是原始作答而非分数。**能不留字段就不留字段** |
| 8 | 某些副作用失败了，要不要让主流程回滚？ | 判断标准：该故障会不会让用户无法完成核心动作。不会就降级 + 告警 + 兜底 |
| 9 | 多指标看板怎么保证口径一致？ | 每个指标的分子分母都要显式定义并写进文档；**代码改动时文档必须同步** |
| 10 | SQL 分组统计漏桶怎么处理？ | 固定桶的维度（顺序与文案）放应用层，SQL 只填数，缺的补 0。**别让前端处理"有几个返回几个"** |
| 11 | Mockito 的 `any()` 和 `anyInt()` 有什么区别？ | `any()` 返回 null，用于原始类型参数会拆箱 NPE。原始类型必须用 `anyInt()`/`anyLong()` 等 |

## 六、可延伸的数据/算法点

### ① 统计分析与 SQL 建模

看板的成绩分布用了 `CASE WHEN` 分桶 + 子查询取每人最高分：

```sql
SELECT bucket, COUNT(1) FROM (
  SELECT CASE WHEN best_score < 60 THEN 'A' ... END AS bucket
  FROM (SELECT MAX(score) AS best_score FROM t_exam_record ... GROUP BY user_id) per_user
) buckets GROUP BY bucket;
```

**这里有个值得深挖的建模问题**：`GROUP BY user_id` 取 `MAX(score)` 是"一人一票"，
但这是**把多次测验压成一次**。如果业务想知道"参与度"，
用 `COUNT(*)` 更合适；想让"多考几次能提分"，`MAX` 才对。

**同一份数据，聚合口径不同，结论完全不同**——这正是数据分析里最容易踩的坑，
而且它有真实业务含义，比刷题网站上的示例表更能讲清楚。

### ② 数据可视化报表

五项指标的口径定义（尤其两个比例的分母）就是报表设计的核心工作。
可以做的延伸练习：**给每个指标补一个"口径说明"字段返回给前端**，
让报表上能 hover 显示"这个数字怎么算的"。
这是真实产品里提升数据可信度的常见做法。

### ③ 机器学习预测与预警

答题记录 + 学时记录合起来可以做**学习成效分析**：
「学时投入」与「答题成绩」是否存在正相关？哪些资源的学习者成绩提升明显？
这是相关性分析，比直接上模型更稳妥，而且是预警模型的前置探索。

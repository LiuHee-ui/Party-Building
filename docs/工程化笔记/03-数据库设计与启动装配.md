# 03 · 数据库设计与启动装配

> 对应产物：`party-server/sql/V1__schema.sql`（16 张表）、`party-boot` 配置与拦截器
> 状态：✅ 表已在真实 MySQL 8.0.17 上执行并验证（16 张表 + 11 个唯一约束）

---

## 一、这个模块解决什么问题

表结构是业务规则的**最后一道防线**。

比如「单条资源单日最多计 2 学时」这条规则，如果只在 Java 代码里判断，
那么任何绕过这个 Service 的写入口都会破坏它。但如果把它变成
`t_credit_daily` 上的 `minutes <= 120` 加唯一约束，**数据库层面就无法产生违规数据**。

**一句话**：能用约束表达的规则，就不要只用代码表达。

## 三、关键决策与取舍

### 决策 1：唯一约束不只是「防重复」，它就是业务规则

项目里有 11 个唯一约束，其中几个是**直接承载业务语义**的：

| 约束 | 承载的业务规则 |
|---|---|
| `t_learn_heartbeat.uk_session_seq(session_id, client_seq)` | **断网补传防重放**：重复上报同一个心跳，会被唯一键挡住 |
| `t_credit.uk_credit_source(user_id, period_type, period_key, source_type, source_id)` | **学时防重复入账**：同一天同一资源的折算分录只有一条 |
| `t_credit_daily.uk_user_resource_date(user_id, resource_id, stat_date)` | 日累计只有一行，配合 `minutes <= 120` 实现单日封顶 |
| `t_exam_record.uk_user_paper(user_id, paper_id)` | 同一份试卷只能提交一次 |

**为什么强调这个**：如果只靠「先 `SELECT` 判断存在，再 `INSERT`」，
在并发下会出问题——两个请求同时查到「不存在」，然后都插入成功。
**唯一约束是并发安全的，先查后插不是。**

正确姿势：**直接 `INSERT`，捕获唯一键冲突异常，再决定是返回已有结果还是报错。**
这就是「乐观插入」模式，比「悲观查询」性能更好也更安全。

---

### 决策 2：逻辑删除与唯一约束的冲突

`deleted` 字段做逻辑删除，但**逻辑删除的行仍然占用唯一索引**。
比如用户 A 被逻辑删除了，再用同一个 `open_id` 注册会失败。

**方案（视业务而定）**：
- 方案 A：唯一索引改为 `(open_id, deleted)` 复合唯一 —— 但 `deleted=1` 的行仍会互相冲突
- 方案 B：删除时把 `deleted` 置为 `id`（一个非 0 的唯一值），这样每条删除记录都不冲突
- 方案 C：审计类数据不做逻辑删除，只做状态标记

**本项目的选择**：党建台账、学时流水属审计类数据，**本来就不该删除**，
所以物理删除的入口不开放，`deleted` 主要用于防止误操作。
**这是一个真实的取舍，面试可以讲「为什么我没用常见方案」。**

---

### 决策 3：复合索引的列顺序

看一个例子：

```sql
KEY `idx_pending` (`org_id`, `biz_type`, `pending`, `created_at`)
```

待审队列的查询是「**本组织范围 + 指定类型 + 未处理**，按提交时间排序」。
列顺序按**等值条件在前、范围/排序条件在后**排列：
`org_id`（等值）→ `biz_type`（等值）→ `pending`（等值）→ `created_at`（排序）。

**反过来写会怎样**：如果 `created_at` 放在前面，索引的排序能力就废了——
因为前面的等值列没确定，后面的排序用不上。

> **面试常问**：「为什么索引不生效？」——很大比例是**列顺序不匹配查询模式**，
> 而不是「忘了加索引」。

---

### 决策 4：审计日志要能单独回答「谁在什么时候改了什么」

`t_audit_log` 有两个索引：

```sql
KEY `idx_biz` (`biz_type`, `biz_id`, `created_at`)      -- 查某条业务的审核历史
KEY `idx_pending` (`org_id`, `biz_type`, `pending`, `created_at`)  -- 查待审队列
```

**为什么 `pending` 要单独做字段而不是靠 `action` 判断**：
待审队列是**最高频**的查询（管理端首页就要用），把它做成一个可索引的字段，
查询就是纯索引扫描。靠 `action != 'APPROVE'` 这种条件是无法有效索引的。

**这条设计的本质**：**把最高频查询的条件显式建模成字段**。

### 决策 5：启动即校验，宁可起不来

```java
@PostConstruct
public void init() {
    if (!StringUtils.hasText(properties.getKey())) {
        throw new IllegalStateException("crypto.key 未配置，敏感字段加密无法启用");
    }
    CryptoUtil.initKey(properties.getKey());
}
```

同类设计还有 `ObjectStorageConfig`：如果 `storage.provider` 配了未实现的值，
启动直接失败而不是运行时才报错。

**为什么**：配置错误在启动时暴露的成本是「改一行重跑」，
在运行时暴露的成本是「线上某个功能静默失效」。
**故障越早暴露越便宜**，这个原则叫 Fail Fast。

---

### 决策 6：ThreadLocal 必须清理

```java
@Override
public void afterCompletion(...) {
    LoginContext.clear();   // 必须清理
}
```

**为什么必须清理**：Tomcat 的线程是**复用的**。如果请求 A 设置了用户身份，
请求 A 结束后没清理，请求 B 复用到同一个线程，就会**读到上一个用户的身份**——
这是经典的身份串号漏洞，而且极难排查（因为表现是「偶发地看到别人的数据」）。

**顺带一个设计约束**：`AuthInterceptor` 只负责「解析身份」，
**数据范围解析交给切面**。职责单一，两类逻辑改动互不影响。

## 四、可迁移的方法论

1. **业务规则尽量下沉到数据结构**：唯一约束、非空约束、默认值。
2. **幂等用「乐观插入 + 捕获冲突」，不用「先查后插」。**
3. **复合索引按「等值在前、范围排序在后」排列表顺序。**
4. **最高频的查询条件，要有独立的索引列。**
5. **配置校验放启动期，不放运行期。**
6. **ThreadLocal 用完必须清**，这是硬性纪律。

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 怎么保证接口幂等？ | 三种：① 唯一键约束（本项目的心跳与学时入账）② 幂等令牌（业务侧生成 token，服务端记录已处理）③ 状态机 + 乐观锁。**核心是找到业务上的唯一标识** |
| 2 | 唯一键冲突应该怎么处理？ | `INSERT` 捕获 `DuplicateKeyException`，而不是先 `SELECT` 再 `INSERT`。后者在并发下不安全 |
| 3 | 逻辑删除有什么坑？ | 与唯一索引冲突、查询必须都带 `deleted=0`（容易漏）、数据量持续增长。**审计类数据建议不删只标记状态** |
| 4 | 复合索引的列顺序怎么定？ | 等值条件列在前，范围/排序列在后；同时考虑选择性（区分度高的列优先） |
| 5 | `EXPLAIN` 里你最看哪些列？ | `type`（连接类型，避免 ALL 全表扫描）、`key`（实际用的索引）、`rows`（扫描行数）、`Extra`（警惕 `Using filesort` 和 `Using temporary`） |
| 6 | 为什么复合索引有「最左前缀」原则？ | B+ 树按列顺序排序。跳过最左列，后面的列在索引里是「无序的」，无法用于定位 |
| 7 | ThreadLocal 的内存泄漏是怎么回事？ | `ThreadLocalMap` 的 key 是弱引用、value 是强引用。key 被回收后 value 无法访问但不会释放。**所以必须显式 `remove()`** |
| 8 | 什么是 Fail Fast？ | 错误在最早可能的时机暴露。启动期校验配置、参数入口校验，都比运行到一半报错成本低 |
| 9 | `@ConfigurationProperties` 和 `@Value` 的区别？ | 前者支持批量绑定、类型转换、松散绑定、JSR-303 校验，适合一组配置；后者适合单个值 |
| 10 | DATE 和 DATETIME 怎么选？ | 只做「按天归属」的统计字段用 DATE（如 `stat_date`）；需要精确时刻的用 DATETIME。**混用会导致跨日统计口径不一致** |

## 六、可延伸的数据/算法点

你选的三个方向在这张表结构上都有落点：

**① 统计分析与 SQL 建模**
- 「学时台账」需要横向聚合：`SELECT user_id, SUM(credit) FROM t_credit GROUP BY user_id`，
  加上组织维度就是两级汇总。
- 进阶练习：用**窗口函数**算「连续未学习天数」——典型的 gaps-and-islands 问题
  （`ROW_NUMBER` 差值法），是面试高频的 SQL 题，而且这里有真实数据场景。

**② 机器学习预测与预警**
- 数据源已经天然具备：`t_learn_record`（学习行为）+ `t_credit`（学时时间序列）
  + `t_user`（身份、民族、组织）。
- 可做的题目：**学习不达标预警**（分类问题，标签是「周期结束时学时是否达标」）、
  **活跃度分层**（聚类，K-Means 或基于 RFM 的规则分层）。
- **注意**：这一块不能直接写进 V1，需要另立 spec——
  它的难点不在算法，而在**特征口径定义**和**样本偏差**
  （民族地区网络条件差，学习行为数据本身就有缺失，不是随机的）。

**③ 数据可视化报表**
- 看板的五个指标已经定义了口径（在册人数、活跃度、达标率、成绩分布），
  这就是报表设计的核心工作——**先把「一个指标怎么算」讲清楚，再谈画什么图**。

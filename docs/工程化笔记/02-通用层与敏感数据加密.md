# 02 · 通用层与敏感数据加密

## 一、这个模块解决什么问题

每个项目都会有一批「到处都要用、但不知道放哪」的东西：统一的返回格式、错误码、异常处理、
时间处理、加解密、脱敏。

如果随手放在 `controller` 包里，很快就会出现「同一个工具类有 3 个版本，改哪个都怕」。
放到独立的 `party-common`，并定下一条规则——**common 不依赖任何业务模块**——
它就成了整个项目的稳定底座。

**一句话**：通用层是「不许放业务逻辑」的地方，这条纪律比里面的工具本身更重要。

## 三、关键决策与取舍

### 决策 1：HTTP 状态码统一 200，业务结果放在 body 的 `code`

**被否决**：REST 语义化状态码（404 表示资源不存在、403 表示无权限……）

**为什么选 200**：
- 客户端只需要**一处**错误处理分支。小程序端拿到响应先看 `code`，不用同时判断
  HTTP 码和业务码两套体系。
- 更实际的原因：**反向代理和 API 网关可能改写 4xx/5xx**。某些网关会把 502 改成 500，
  客户端拿到的状态码就不可信了。body 里的业务码不会被中间件碰。

**代价（要主动说出来）**：监控和日志无法只靠 HTTP 码判断错误率，需要在网关层额外解析 body。
这是一个真实的取舍，不是「200 更好」。

---

### 决策 2：错误码分段，而不是从 1 开始递增

```
0        成功
1000-1999 参数与校验
2000-2999 认证与登录态
3000-3999 权限与数据范围
4000-4999 业务规则
5000-5999 系统与外部依赖
```

**为什么分段**：看到 `3002` 就知道是权限问题，看到 `4004` 就知道是业务规则问题，
**不用查文档**。分段是给人看的，不是给机器看的。

**顺带**：每个错误码带 `messageKey` 而不只是中文文案。这是为多语言准备的——
客户端按当前语言渲染 `messageKey`，而不是靠服务端返回中文。
**接口设计要为后续需求留出语义位置**，这个习惯比具体技术更重要。

---

### 决策 3：AES-GCM 而不是 AES-ECB / CBC

这是本篇最值得记住的一个点。

| 模式 | 问题 |
|---|---|
| ECB | **同样明文块产生同样密文块**。加密一张图片，能直接看出轮廓；加密手机号，能看出哪些人号码相同。**绝对不要用** |
| CBC | 需要额外的 HMAC 做完整性校验，否则密文被篡改无法发现 |
| **GCM** | **认证加密（AEAD）**：加密的同时生成认证标签，密文被改一个 bit，解密直接失败。一次搞定机密性 + 完整性 |

**代码里的两个细节**：

```java
// 1. 随机 IV，前置到密文
byte[] iv = new byte[12];
RANDOM.nextBytes(iv);          // 12 字节是 GCM 推荐长度
...
System.arraycopy(iv, 0, result, 0, 12);   // 解密时要能拿到 IV

// 2. 密钥未初始化直接抛异常
if (current == null) throw new BizException(..., "加密密钥未初始化");
```

**为什么要随机 IV**：同一个密钥下，**IV 复用会让 GCM 彻底失效**（不只是密钥泄露，
攻击者还能伪造任意密文）。单元测试里专门验证了「同一明文两次加密结果不同」——
这条测试保证的就是随机 IV 生效了。

**为什么密钥缺失要抛异常而不是用默认值**：用默认密钥等于没加密。
**启动就失败，好过静默地用空密钥加密了一堆数据。**

### 决策 4：手机号存「密文 + 末四位冗余」

**表结构**：
```sql
`mobile_cipher` VARBINARY(128)  -- AES-GCM 密文
`mobile_tail`   VARCHAR(4)      -- 明文末四位
```

**被否决**：明文存储，在展示层脱敏。

**为什么**：
- 列表页要显示 `138****8000`，如果用「密文 + 展示层脱敏」，**每一行都要解密**
  ——性能差，而且**每次解密都是敏感数据访问**，要写审计日志，列表页会刷出大量无意义日志。
- 存末四位后，列表直接读明文末四位，**不解密、不进审计**。

**这条设计的本质**：**把「安全约束」下沉到数据结构里，而不是靠调用方自觉**。
只要有人忘了脱敏，明文就泄露了；但存的是密文 + 末四位，想泄露也泄露不了。

> 面试可以这样讲：**能用数据结构保证的事情，不要用代码规范保证。**

---

### 决策 5：脱敏展示不算「敏感数据访问」

配套设计了 `t_sensitive_access_log`，但明确规定：**取末四位不写日志，只有解密或修改才写**。

**为什么**：审计日志的价值在于「异常可发现」。如果列表浏览都记，
日志会被淹没，真正需要追查的记录反而找不到。**审计要有边界，否则等于没有。**

---

### 决策 6：组织树用「祖先路径」而不是递归查询

**场景**：组织是三层树（党委 → 党总支 → 党支部）。管理员只能看「本组织及下辖组织」的数据。

**表结构**：`t_org.path` 存 `/1/12/35/`。

**查询**：
```sql
SELECT id FROM t_org WHERE path LIKE '/1/12/%'
```

**被否决**：`parent_id` 递归查询（`WITH RECURSIVE`）。

**为什么**：
- 递归查询每次请求要**多轮数据库交互**，或者用 CTE 扫描整棵树。
  在 1000 人规模的组织下，看板查询会明显变慢。
- 路径匹配是一次索引扫描，`idx_path(path)` 直接走索引。

**代价（要主动说）**：组织移动时，**整棵子树都要重写 path**。
这是一次性的写放大，换来的是所有读路径都变成 O(1) 索引查询。
**读多写少的场景，这个取舍是划算的。**

**测试里的一个边界**：`/1/120/` 不能被误判为 `/1/12/` 的下级。
因为路径带尾斜杠，`"/1/120/".startsWith("/1/12/")` 是 `false`——**尾斜杠不是装饰，是正确性的一部分**。

---

### 决策 7：全局统一 `Asia/Shanghai` 切日

**业务后果**：学时统计里有一条规则是「单条资源单日最多计 2 学时」。
**如果「日」的边界不统一，这条规则就是不确定的**——23:50 学的那一段，算今天还是明天？

**代码**：`DateUtil.statDateOfInstant(instant)` 统一由绝对时刻推导统计日。

**单元测试专门验证了跨日边界**：
```
UTC 15:59:59 → 北京时间 23:59:59 → 归属当日
UTC 16:00:00 → 北京时间次日 00:00 → 归属次日
```

> **这是我认为最值得学的一课**：凡是涉及「时间」的业务规则，
> **一定要有唯一的时钟和唯一的时区**。分布式系统里时间问题是 bug 高发区，
> 而根源往往是「大家都在各自的地方 `new Date()`」。

## 四、可迁移的方法论

1. **能靠数据结构保证的约束，不要靠代码规范保证。**（密文 + 末四位）
2. **凡是「几处都要写一遍」的东西，都要收拢到一个唯一实现。**（错误码、时间工具）
3. **对外契约要把「给人看」和「给机器看」分开。**（`code` 给机器、`messageKey` 给人）
4. **加密方案的选择要能说出「为什么不是那个」。**（GCM vs ECB/CBC）

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | AES 的 ECB、CBC、GCM 有什么区别？ | ECB 相同明文块产生相同密文，不可用；CBC 需额外 HMAC 做完整性；GCM 是认证加密，一次搞定机密性 + 完整性 |
| 2 | 为什么 GCM 的 IV 绝对不能复用？ | IV 复用会泄露异或关系，且能伪造任意密文（伪造认证标签）。所以必须随机生成并随密文保存 |
| 3 | 加密的密钥应该放在哪？ | 不放代码仓库、不放配置文件明文。用环境变量或密钥管理服务（KMS）。配置里只放开发密钥 |
| 4 | 敏感字段怎么做脱敏展示又不影响性能？ | 加密存储 + 冗余明文末几位，列表直接读冗余字段，避免逐行解密 |
| 5 | 为什么接口返回 HTTP 200 而不是语义化状态码？ | 客户端单一错误分支；中间件可能改写 4xx/5xx。代价是监控需要解析 body |
| 6 | 树形结构在数据库里怎么存？ | 邻接表（parent_id，写简单读难）、路径枚举（path，读写均衡）、闭包表（查询最灵活但表大）、嵌套集（读快写慢）。**本项目的组织树读多写少，选路径枚举** |
| 7 | 路径枚举的缺点是什么？ | 节点移动要重写整棵子树的 path。适合读多写少的场景 |
| 8 | 为什么业务规则要绑定唯一时区？ | 否则「按天统计」这类规则的含义不确定。测试要覆盖跨零点边界 |
| 9 | `@RestControllerAdvice` 和 `@ControllerAdvice` 的区别？ | 前者 = 后者 + `@ResponseBody`，返回值直接序列化为 JSON |
| 10 | 业务异常和系统异常为什么要分开处理？ | 业务异常是预期内的，记 warn 并返回明确错误码；系统异常是缺陷，要记 error + 堆栈，对外只返回通用错误码，**不暴露内部信息** |

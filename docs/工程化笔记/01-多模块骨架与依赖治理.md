# 01 · 多模块骨架与依赖治理

> 对应代码：`party-server/pom.xml` 与 8 个子模块的 `pom.xml`
> 状态：✅ 完成，`mvn compile` BUILD SUCCESS

---

## 一、这个模块解决什么问题

一个人写的小项目通常会这样开头：一个 `src/main/java` 目录，下面按 `controller`、
`service`、`mapper` 分三层。写着写着就发现——**同一个包里的东西越堆越多，改一处不知道会
影响谁**。

这个问题在团队里会被放大。多模块的价值不是「显得专业」，而是**用编译器帮你守住边界**：
如果 `party-learn` 想直接调用 `party-org` 的 Mapper，编译期就报错，不需要靠 code review 去发现。

**一句话**：模块划分 = 把「不该耦合」这件事从人的自觉变成机器的强制。

## 二、涉及的工程能力

| 能力 | 具体内容 |

| Maven 多模块 | 父 POM、`dependencyManagement`、聚合与继承的区别 |
| 依赖治理 | 单向依赖、无环校验、依赖白名单 |

## 三、关键决策与取舍

### 决策 1：模块化单体，不是微服务

**选择**：Spring Boot 单体 + 按业务域拆 Maven 模块。

**为什么不拆微服务**：
- 这个产品是「单组织、单数据库、单团队」。微服务的收益（独立扩缩容、独立部署、技术异构）
  一个都用不上，成本（注册中心、网关、链路追踪、分布式事务）却全都要付。
- 更实际的理由：**拆服务容易，合服务很难**。等真的需要拆的时候，模块边界清晰的单体
  拆起来是低成本的；反过来，一开始就拆错的服务合并起来是灾难。

**面试会问**：什么情况下应该拆微服务？
答题要点：先看组织规模（康威定律）——**如果团队不到 5 个后端，微服务基本是负收益**；
再看是否有独立扩缩容或技术异构的真实诉求。

---

### 决策 2：按业务域拆，不按技术层拆

**选择**：`party-auth` / `party-org` / `party-learn` / `party-exam` 这样按业务域分。

**被否决**：`party-controller` / `party-service` / `party-mapper` 按技术层分模块。

**为什么**：
- 按技术层分模块，会导致**任何一次业务改动都要同时改 3~4 个模块**——
  加一个字段，controller、service、mapper 三个模块都要动。模块化带来的隔离优势完全消失。
- 按业务域分，一个需求的改动通常只落在一个模块内。这才是模块化应有的效果。

---

### 决策 3：依赖方向靠「能力接口」而不是「反向依赖」打破环

这一条是实践中最有价值的。

**问题**：审核流水表 `t_audit_log` 是唯一的审核落点，但**状态迁移要发生在不同模块的表上**——
资源表在 `party-content`、用户表在 `party-auth`。如果让 `party-audit` 依赖这些业务模块
去改状态，依赖图就成环了；而且**每新增一种可审对象，都要改 audit 模块**。

**选择**：依赖倒置。`party-audit` 只定义能力接口 `AuditableHandler`，
业务模块实现它并注册为 Spring Bean；audit 在审核时回调，不关心实现方是谁。

```
party-audit (定义 AuditableHandler + 拥有 t_audit_log)
      ↑ 被依赖
party-content / party-auth / party-interact (实现接口)
```

**收益**：
- 依赖图是 DAG，无环
- 新增可审对象时，audit 模块**零改动**
- 待审队列 = `t_audit_log` 里 `pending=1` 的记录，audit **不需要访问任何业务表**

**被否决**：让 audit 直接依赖各业务模块 —— 成环，且每加一种可审对象就要改 audit。

> **这一处我在写 POM 时发现了 plan 文档的错误**：原文写的是 `audit → auth`，
> 但 `auth` 要实现 `AuditableHandler` 并调用 `AuditService`，真实方向是 `auth → audit`。
> 两者相加成环。修正为 `audit → common`（不依赖任何业务模块）。
>
> **可以记下来的经验**：依赖方向不能靠想，要写进 POM，让编译器验证。
> 纸上的架构图经常是错的。

## 四、可迁移的方法论

1. **依赖白名单写成显式列表**，而不是「大概记得不能循环依赖」。
   这份白名单本身就是最好的架构文档：
   ```
   party-common  ← 无依赖
   party-audit   → common
   party-auth    → common, audit
   party-org     → common, auth
   party-learn   → common, auth, org, content
   ```
2. **跨模块只准调接口，不准碰对方的 Mapper 和实体**。这条规则能挡住 90% 的隐性耦合。
3. **同模块内 Service 可以互调，跨模块不行**。给「方便」留一个口子，但只在模块内部。

换到任何一个中小型项目，这套划分方式都能直接用。

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | Maven 的 `dependencyManagement` 和 `dependencies` 有什么区别？ | 前者只声明版本不引入依赖，用于统一版本；后者真正引入。父 POM 用前者管理子模块版本 |
| 2 | Maven 聚合（`<modules>`）和继承（`<parent>`）是一回事吗？ | 不是。聚合是为了**一次构建多个模块**，继承是为了**复用配置**。可以只有其一 |
| 3 | 怎么保证多模块项目不出现循环依赖？ | 分层 + 白名单 + CI 里加 `maven-enforcer-plugin` 的 `banCircularDependencies` 规则，让构建失败 |
| 4 | 循环依赖怎么打破？ | 三种手段：① 提取公共依赖到下层模块 ② 依赖倒置（定义接口由上层实现）③ 事件/消息解耦。本项目用的是第 ② 种 |
| 5 | 什么时候不该拆微服务？ | 团队规模小、无独立扩缩容诉求、无技术异构需求时。**拆的收益要能覆盖分布式带来的复杂度成本** |
| 6 | 模块化单体的边界怎么验证？ | 让编译器验证：跨模块访问对方 Mapper 时编译不过。比靠 code review 可靠 |

## 六、可延伸的数据/算法点

- **依赖图本身是个有向图**，可以用拓扑排序做构建顺序优化。
  这不是玩具题——大型项目的增量构建就是靠依赖图决定编译顺序的。
  你可以在 CI 里实现一个小工具：解析各模块 POM，输出拓扑序与关键路径。
- 「无环校验」本质是**图算法**（DFS 判环 / Kahn 算法），
  和你数据算法方向的基础是同一套东西。把它写进简历里的技术点是真实可讲的。

## 一、这个模块解决什么问题

「学时」是这个产品的**考核凭证**——它会直接影响党员的评价、达标与否。
一旦学时能被刷，整个系统的公信力就没了。

所以这个模块的本质不是「记录学习时长」，而是**设计一套能挡住作弊、又不误伤正常用户的计量规则**。

难点在于两个方向同时收窄：

| 收得太松 | 收得太紧 |
|---|---|
| 挂机刷时长 | 弱网用户（民族地区网络差）拿不到学时 |
| 脚本高频上报 | 切出去接个电话就被扣掉 |
| 改客户端时间 | 锁屏恢复后整段不算 |

**一句话**：这不是技术问题，是把业务规则设计到「作弊成本高于收益、正常使用不受影响」的平衡点。

## 三、关键决策与取舍

### 决策 1：客户端上报的是「增量」，不是「累计」

**选择**：客户端每次上报「距上次上报多少秒」，服务端累加。

**被否决**：客户端上报「当前累计学习了多少秒」。

**为什么**：累计值是**客户端完全可控的**。用户改一个数字就能把累计值改成 100 小时。
增量值虽然也能伪造，但服务端有三道闸门拦它：限流（上报频率）、
单次上限（单次最多计 60 秒）、日封顶（单条资源单日最多 120 分钟）。
**三道闸门叠加，作弊的时间成本远大于实际学习。**

> **可迁移的原则**：凡是客户端能直接决定数量级的数值，都不要直接采信。
> 让它上报增量，由服务端决定「这次能计多少」。

---

### 决策 2：超长间隔「截断」而不是「丢弃」

这是本模块最需要权衡的一处。

```java
if (deltaSec > MAX_DELTA_SEC) {
    return Decision.truncated(MAX_DELTA_SEC);   // 而不是 reject
}
```

**如果丢弃会怎样**：民族地区网络不稳定，用户断网 10 分钟后恢复，
一次性补传一个 `deltaSec = 600` 的心跳——直接丢弃意味着**这 10 分钟完全白学**。

**如果全额接受会怎样**：挂机党锁屏一小时，回来上报 `deltaSec = 3600`，
一次就拿到 60 分钟学时。

**截断是两者的平衡点**：接受这条心跳，但只计 60 秒。
弱网用户拿到了少量补偿，作弊者拿到的是「单个心跳上限」，损失可控。

> 这个取舍值得记住：**规则设计不要只有「接受/拒绝」两档，中间态往往才是最优解。**

---

### 决策 3：失焦用「累计后扣超出」，而不是逐次判断

口径：**累计失焦超过 600 秒后，只扣超出部分。**

```java
public static int effectiveSec(int totalFocusedSec, int totalUnfocusedSec) {
    int deductible = Math.max(0, totalUnfocusedSec - UNFOCUS_FORGIVE_SEC);
    return Math.max(0, totalFocusedSec - deductible);
}
```

**为什么不能逐次判断**：用户可能 10 次各失焦 90 秒（合计 900 秒）。
每次单独看都「不长」，逐次判断全都放行；累计口径才能抓住这种情况。

**为什么给 600 秒豁免**：移动端学习，切后台回消息、接电话是**正常行为**。
不给豁免，正常用户的学时会被大量误扣，投诉会比作弊更麻烦。

**测试里专门验了这条**：`manyShortUnfocusAccumulate` —— 10 次各 90 秒，
最终扣掉超出的 300 秒。

### 决策 4：封顶判定必须加行锁

```java
CreditDaily daily = creditDailyMapper.selectForUpdate(userId, resourceId, statDate);
```

**不加锁会发生什么**：

```
线程 A: 查询当日已计 110 分钟 → 剩余额度 10 分钟
线程 B: 查询当日已计 110 分钟 → 剩余额度 10 分钟
线程 A: 写入 120 分钟 ✓
线程 B: 写入 120 分钟 ✓          ← 两个都以为自己只加了 10 分钟
```

单个用户的心跳可能因为重试或客户端 bug 并发到达，不加锁就会突破封顶。

**代价**：`FOR UPDATE` 会阻塞同一行的并发访问。但锁的范围是
**「用户 × 资源 × 日期」这一行**，竞争面极小，可以接受。

> 注意 `selectForUpdate` 返回 null 时的处理：需要先插入再重读。
> 插入要捕获 `DuplicateKeyException`——**并发下两个请求都可能发现行不存在并尝试插入**，
> 唯一键会挡住第二个。这是「乐观插入」的典型用法。

---

### 决策 5：幂等靠「唯一约束 + 前置查询」双保险

```java
// 前置查询：命中就直接返回首次结果（快路径）
Integer prior = heartbeatMapper.selectAcceptedSec(sessionId, clientSeq);
if (prior != null) return buildReplayResult(session, prior);
```

加上 `t_learn_heartbeat` 上的 `uk_session_seq(session_id, client_seq)` 唯一约束作为**最终保障**。

**为什么要两层**：
- 前置查询是**性能优化**——重复上报是高频场景（弱网重传），让它走快路径，不写库
- 唯一约束是**正确性保障**——前置查询在并发下不可靠（两个请求可能同时查到 null），
  唯一键才真正保证不会重复

> **「先查后插」在并发下不安全，但不能因此就不查。**
> 查询做性能优化、约束做正确性保障，两者是互补的，不是二选一。

---

### 决策 6：校验顺序决定日志可读性

```java
if (clientSeq <= maxAcceptedSeq) → REPLAY          // 第 1 步
if (deltaSec <= 0)               → OUT_OF_ORDER
if (间隔 < 3 秒)                  → RATE_LIMITED     // 第 2 步
if (deltaSec > 60)               → 截断             // 第 3 步
```

**为什么重放要排在最前面**：重放是**正常现象**（弱网重传），
而限流是**可疑现象**。如果顺序反了，一个重传的心跳会被记成「限流」，
监控上就看不出到底有多少真实的重传、多少可疑的刷量。

**顺序也是口径的一部分**——同一条请求被判定成不同的原因，运维看到的图景完全不同。

---

### 决策 7：进度口径用「记录累计」而不是「会话累计」

这一条是**测试抓出来的**。

我最初用「会话累计秒数」算完成度，测试断言 `15 秒 / 600 秒 = 2.50%` 却得到 19.17%——
因为测试夹具里的会话已经累计了 100 秒。

**问题在哪**：完成度描述的是「这份资源学到哪了」，它必须**跨会话、跨天延续**。
用会话累计，用户第二天重看同一视频，进度条会从零开始。

**正确口径**：`t_learn_record.valid_sec`（用户 × 资源累计）。

> **这类 bug 单靠读代码很难发现**，因为它不是崩溃，只是数字不对。
> 断言具体数值（而不只是断言「不为空」）才能抓住它。

## 四、可迁移的方法论

1. **不让客户端决定数量级**：上报增量，由服务端决定计入多少。
2. **限流不要只有两档**：接受 / 截断 / 拒绝，中间态往往最优。
3. **阈值类规则优先用累计口径**，逐次判断会漏掉「多次小幅超限」。
4. **计数封顶必须加行锁**，先查后改在并发下必然出错。
5. **幂等 = 快路径查询（性能）+ 唯一约束（正确性）**，两者互补。
6. **校验顺序是口径的一部分**，决定了监控看到什么。
7. **聚合口径要跨会话延续**，别用临时状态算长期指标。

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 怎么防止用户刷时长？ | 三道闸门：限流（频率）+ 单次上限（数量级）+ 日封顶（总量）。**客户端只报增量** |
| 2 | 接口幂等怎么实现？ | 找到业务唯一标识做唯一约束；查询做快路径优化，约束做正确性保障。**别只靠先查后插** |
| 3 | `SELECT ... FOR UPDATE` 的锁范围是什么？ | InnoDB 下走主键/唯一索引时是行锁；走非索引列或范围条件可能升级为间隙锁甚至表锁。**务必走索引** |
| 4 | `FOR UPDATE` 有什么代价？ | 阻塞同行的并发访问，持锁时间长会拖慢系统。只在必要处用，且尽量缩小锁定行 |
| 5 | 插入时并发冲突怎么处理？ | 捕获 `DuplicateKeyException` 后重读。这是乐观插入，比「先查再插」更可靠 |
| 6 | 什么是累积阈值规则？为什么需要？ | 多次小幅超限累计后才会触发。逐次判断会漏掉「每次都不长但总量很大」的情况 |
| 7 | 统计口径为什么必须固定时区？ | 否则「单日封顶」的含义不确定。本项目固定 Asia/Shanghai，测试覆盖跨零点 |
| 8 | 一个业务动作要写多张表，怎么保证一致性？ | 放同一事务，任何一个失败整体回滚。**避免「心跳记了但学时没算」** |
| 9 | 多条校验规则的顺序重要吗？ | 重要。顺序决定了同一条请求被归类成什么原因，直接影响监控与排障 |
| 10 | 怎么设计「既不误伤又防作弊」的规则？ | 给正常行为留豁免额度（如失焦 600 秒），只惩罚超出部分。**规则要能解释给用户听** |

## 六、可延伸的数据/算法点

### ① 统计分析与 SQL 建模（你的第一方向）

- **连续学习天数**（streak）是经典的 gaps-and-islands 问题：
  ```sql
  SELECT user_id, COUNT(*) AS streak_days FROM (
    SELECT user_id, stat_date,
           DATE_SUB(stat_date, INTERVAL ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY stat_date) DAY) AS grp
    FROM (SELECT DISTINCT user_id, stat_date FROM t_credit_daily WHERE minutes > 0) t
  ) s GROUP BY user_id, grp ORDER BY streak_days DESC;
  ```
  这不是刷题网站上的抽象表——**这里有真实的日累计数据可以直接跑**。同一天缺卡算断签，
  这个业务问题本身就要求你处理「日期连续性」，比背模板有说服力。

### ② 机器学习预测与预警（你的第二方向）

数据基础已经就绪：`t_credit_daily`（时间序列）+ `t_learn_session`（行为细节）
+ `t_user`（身份、民族、组织）。

可以做的题目：**周期结束前预测党员是否达标**。
特征工程是真正的难点，而且这里有几个很值得讲的点：

- **样本偏差**：民族地区网络条件差，学习行为数据本身就有缺失，**且缺失不是随机的**
  （网络差的地区缺得更多）。直接丢缺失样本会让模型系统性高估偏远地区的达标率。
- **特征口径**：用「日均学时」还是「学习天数」？用「最近 7 天」还是「全周期」？
  不同口径训出来的模型适用场景完全不同。
- **标签口径**：达标与否是二分类，但**判定时点很关键**——
  用「周期结束时的结果」做标签，就无法在周期中途做预警（信息泄漏）。

**提醒**：这块必须另立 spec，**不要为了简历硬塞进 V1**。
它的难点不在算法（逻辑回归足够），而在特征口径与样本偏差的处理——
面试时能讲清楚这两点，比说「我用了 XGBoost」有说服力得多。

### ③ 数据可视化报表（你的第三方向）

看板的五个指标（在册人数、活跃度、达标率、成绩分布）已经定义好口径。
报表设计的核心工作不是画图，是**先把「一个指标怎么算」讲清楚**——
本模块里「单条资源单日封顶 120 分钟」就是一个必须说清的口径，
否则用户看到的「本周学时」和管理员算出来的对不上，信任就没了。

# 08 · 联调实录：为什么单测全绿，系统还是跑不起来

> 对应产物：`party-server/scripts/smoke_test.py`（64 项端到端检查）
> 状态：✅ **64 项全通过，0 失败**；单元测试 224 个同时全绿

---

## 一、这一篇为什么值得单独写

前面 7 篇都是模块内部的工程化。这一篇记录的是**把系统真正跑起来之后抓到的问题**。

当时的处境很有代表性：

```
单元测试：224 个，全绿
启动装配测试：通过
→ 于是开始联调
→ 第一个接口就报 5000
```

**单测全绿不代表系统能跑。** 单测里每个 Mapper 都是 mock 的，
所以 SQL 语法、参数绑定、字段精度、配置项拼写、环境变量覆盖——
这些"只在真实运行时才存在"的问题，单测一个都碰不到。

这一轮一共抓出 **7 个真实缺陷**。下面按「问题 → 现象 → 根因 → 修法」记录，
每一类都值得记住。

---

## 二、七类只在运行时暴露的缺陷

### 缺陷 1：JDBC 参数用了服务端的字符集名

```yaml
# 错
url: jdbc:mysql://...?characterEncoding=utf8mb4
```

**现象**：所有数据库操作失败，抛
`WrongArgumentException: Unsupported character encoding 'utf8mb4'`。

**根因**：`utf8mb4` 是 **MySQL 服务端**的字符集名。
`characterEncoding` 这个参数要求的是 **Java 侧**的字符集名，只认 `UTF-8`。
驱动会自己和服务端协商 utf8mb4，不需要在这里指定。

**修法**：`characterEncoding=UTF-8`。

> **值得记的点**：这个错在启动阶段不报，只有第一个真正访问数据库的请求才报。
> 而全局异常处理器把它包成了「系统繁忙」，从客户端完全看不出是配置问题——
> **必须去看服务端日志**。

---

### 缺陷 2：惰性解析 + 「默认值是空」= 静默的功能失效

这是本轮最值得讲的一个。

**设计**：`LoginContext.visibleOrgIds` 默认是空列表；
数据范围由 `@DataScoped` 注解 + 切面在方法调用前惰性解析。

**现象**：待审队列接口**返回 0 条，不报错**。而数据库里明明有待审记录。

**根因**：`AuditController.pagePending` **忘了标注 `@DataScoped`**。
于是 `visibleOrgIds` 停在默认的空列表上，而业务代码把空列表解释为
「无任何可见组织」→ 返回空结果。

**注意这里的两层问题**：
1. 忘了标注注解 → 靠纪律保证的事情必然会忘
2. 「尚未解析」和「解析结果确为空」**用了同一个值表示** → 无法区分

**修法**：把数据范围解析从「惰性 + 注解」改成**在拦截器里对每个已登录请求统一解析**，
并删掉 `@DataScoped` 与 `DataScopeAspect`。

**代价**：每请求多一到两次组织查询。
**收益**：消除「忘了标注」这一整类缺陷。

> **这是本文最重要的一条经验**：
> **安全相关的上下文不应该依赖"记得标注注解"这种纪律。**
> 而且**状态不要用"值本身"来表达**——「未初始化」和「初始化为空」必须能区分，
> 否则错的那一侧往往是"静默放行"或"静默拦截"，两者都极难排查。

---

### 缺陷 3：`NOT NULL` 加在了「确实还没有值」的字段上

**现象**：第一次上报学习心跳报
`Field 'last_end_at' doesn't have a default value`。

**根因**：`t_learn_session.last_end_at` 定义为 `DATETIME NOT NULL`，
但会话是**客户端进入播放页时就创建**的，此时**还没有任何心跳被接受**，
这个字段在语义上就是空的。

而我在代码里刻意把它写成 `null`，因为限流逻辑需要区分
「从未接受过心跳」（不限流）和「上次接受于某时刻」。

**修法**：把列改为可空。**代码是对的，约束是错的。**

> **判断依据**：`NOT NULL` 表达的是"这个业务对象一定有此属性"。
> 如果一个字段的"没有值"是有意义的业务状态，它就应该可空。
> **不要为了"看起来更严谨"而加 NOT NULL。**

---

### 缺陷 4：动态 SQL 标签漏了 `<script>` 包裹

```java
// 错：MyBatis 不会解析 <foreach>，整段当纯文本 SQL
@Select("""
        SELECT id, name FROM t_org WHERE id IN
        <foreach collection="ids" item="oid" open="(" separator="," close=")">#{oid}</foreach>
        """)
```

**现象**：`BindingException: Parameter 'oid' not found. Available parameters are [ids, param1]`。

**根因**：注解形式的 `@Select` / `@Update` 使用 `<if>` / `<foreach>` 等动态标签时，
**必须用 `<script>...</script>` 包起来**，否则 MyBatis 不进入 XML 解析分支。

**修法**：加 `<script>`。

> **顺带一个自查清单**：项目里所有带动态标签的注解 SQL 都要有 `<script>`。
> 这一条还容易"漏一个、跑很久"——因为它只在特定分支触发时才是错。
> 我在同一批文件里逐个核对过，只有这一处漏了。

---

### 缺陷 5：两个枚举编码撞车（最隐蔽的一个）

**现象**：学时榜**永远是空的**。Redis 里有键，但查不到数据。不报任何错。

**根因**：项目里有两个含义完全不同的枚举，编码却都是 1 开头：

| 枚举 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| `PeriodType`（学时统计口径） | 自然年 | 五年规划期 | — | — |
| `RankingPeriodRange`（榜单换榜周期） | 周 | 月 | 季 | 年 |

学时入账时我把 `PeriodType.NATURAL_YEAR.getCode()`（=1）当成榜单周期传进去，
于是学时被写进了 **`rank:1:learn:1:2026:3`**（周榜），
而查询读的是 **`rank:1:learn:4:2026:3`**（年榜）。

**两个键都是合法的 Redis 键，写入和读取都不报错，只是永远对不上。**

**修法**：单独定义 `common/enums/RankingPeriodType`，
并在 `PeriodRange` 里把常量指向它，同时加编码校验。
在 `CreditServiceImpl` 的注释里明确写出「这里必须用 RankingPeriodType.YEAR，
不能用 PeriodType.NATURAL_YEAR」。

> **这类问题为什么可怕**：
> - 没有异常、没有错误日志、没有 warn
> - 监控看到的只是「榜单功能没数据」，而不是「有 bug」
> - 单元测试验不出来（mock 掉了 Redis，且左右两边各自都"对"）
>
> **防御手段只有一条：让「不能混用」这件事有类型层面的表达。**
> 两个含义不同的维度，**不要复用同一套整数编码**，哪怕它们碰巧长得一样。

### 缺陷 6：判定精度超过了存储精度

**现象**：客户端明明每隔 3.2 秒发一次心跳，却时不时被判 `RATE_LIMITED`
（阈值是 3000 毫秒）。

**根因**：`last_end_at` 用的是 `DATETIME`（**秒精度**），
而 MySQL 对小数秒是**四舍五入**而不是截断：

```
真实接受时刻  22:31:04.700  →  存成 22:31:05   （进位了 300ms）
下次心跳到达  22:31:07.900
间隔算出来 =  2900ms  <  3000ms  →  误判限流
```

**修法**：`last_end_at` 改为 `DATETIME(3)`（毫秒精度）。

> **通用原则：判定精度不能超过存储精度。**
> 用一个秒级的时间戳去做毫秒级的间隔比较，必然出现"随机"的误判——
> 而且这种误判表现为"偶尔失败"，最难复现、最难归因。

---

### 缺陷 7：环境变量静默覆盖了配置文件

**现象**：配置里明明写的是 `server.port: 8080`，日志却是
`Tomcat initialized with port 60533`，然后启动失败说端口被占用。

**根因**：运行环境（IDE / 启动器）注入了一个环境变量 **`SERVER__PORT=60533`**，
Spring Boot 的**宽松绑定**把它解析成了 `server.port`，
而**环境变量的优先级高于 application.yml**。

**修法**：命令行显式传 `--server.port=8080`（命令行参数优先级最高）。

> **值得记的排查思路**：配置没生效时，**先怀疑"有没有更高优先级的来源覆盖了它"**。
> Spring Boot 的属性优先级顺序是：
> 命令行参数 > 环境变量 > 配置文件 > 默认值。
> 用 `env | grep -i` 把可疑的环境变量捞一遍，通常一分钟就能定位。

## 三、顺带修掉的三个测试自身缺陷

联调时也要警惕「"失败"的到底是系统还是测试」。这一轮有 3 个失败项是**测试写错了**：

| 现象 | 真实原因 |
|---|---|
| 4 次心跳只计入 1 分钟 | 测试**连续发心跳没等待**，被限流拦了——**这是服务端正确行为** |
| 得分断言"100.00"失败 | `BigDecimal` 的 JSON 序列化形式是 `100.0`。**断言数值而不是字符串表示** |
| 截断测试拿到 RATE_LIMITED | 同上，没等够 3 秒 |

> **判断标准**：失败时先问「服务端这个行为是不是合理的」。
> 如果合理，就是测试的期望写错了。
> **把正确行为当缺陷去"修"，是联调里最危险的事。**

## 四、可迁移的方法论

1. **单测全绿 ≠ 系统能跑。** 必须有端到端的冒烟测试，且它要连真库、真缓存。
2. **安全上下文不要惰性初始化。** 依赖"记得标注注解"的设计一定会漏。
3. **「未初始化」和「初始化为空」必须能区分**，不能用同一个值表示。
4. **`NOT NULL` 只加在业务上必然有值的字段上**；"没有值"本身是状态时就要可空。
5. **注解形式的动态 SQL 必须有 `<script>` 包裹。**
6. **含义不同的维度不要复用同一套整数编码**——这是静默错误的高发区。
7. **判定精度不能超过存储精度。**
8. **配置没生效时先查优先级覆盖**（命令行 > 环境变量 > 配置文件）。
9. **联调失败先判断是系统错了还是测试错了。**

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 单元测试都通过，为什么还要集成测试？ | 单测 mock 掉了外部依赖，测不到 SQL 绑定、配置拼写、字段精度、环境覆盖。**这些只在真实运行时存在** |
| 2 | JDBC 连接串里的 `characterEncoding` 该写什么？ | Java 字符集名 `UTF-8`。`utf8mb4` 是 MySQL 服务端名，写了会抛 `UnsupportedEncodingException` |
| 3 | MyBatis 注解里怎么用动态 SQL？ | 用 `<script>` 包裹才能启用 XML 解析。漏了会报 `Parameter 'xxx' not found` |
| 4 | 怎么设计数据权限才不容易漏？ | ① 范围解析只有一处实现 ② 不要依赖"记得标注注解" ③ 空集必须显式处理，不能退化成"不加条件" |
| 5 | 「未初始化」和「初始化为空」混用会出什么问题？ | 无法区分两种语义，错误的一侧通常是静默放行或静默拦截。**用独立标志位表达状态** |
| 6 | `DATETIME` 和 `DATETIME(3)` 怎么选？ | 看这个字段要参与什么精度的比较。做毫秒级间隔计算就必须用 `(3)`，否则秒级四舍五入会造成随机误判 |
| 7 | Spring Boot 配置没生效，怎么排查？ | 按优先级从高到低查：命令行参数 → 环境变量（`SERVER__PORT` 这类）→ 配置文件 → 默认值 |
| 8 | 两个枚举编码相同会有什么后果？ | 传参时错用不会报编译错、也不会运行时报错，只会"数据写到了另一个地方"。**用类型区分维度，不要复用编码** |
| 9 | 联调时接口返回「系统繁忙」，怎么定位？ | 全局异常处理器会吞掉真实原因，**必须看服务端日志的堆栈**，从 `Caused by` 往下找根因 |
| 10 | 集成测试失败了，第一步做什么？ | 先确认服务端这个行为**是否合理**。合理就是测试期望写错了——把正确行为当 bug 去修最危险 |

## 六、可延伸的数据/算法点

- **这一轮暴露的问题本质上是"状态机 + 类型安全"问题**：
  「未解析 vs 解析为空」「秒精度 vs 毫秒精度」「两个枚举编码撞车」，
  三者的共同点是**用同一个表示承载了两种语义**。
  这在数据建模里是同一个主题：**码值设计**。
- 你选的「统计分析与 SQL 建模」方向可以直接从这里切入：
  统计口径（`PeriodType`）和展示周期（`RankingPeriodType`）**是两张维度表**，
  在数据仓库里它们会被建成两个独立维度，绝不会共用一套码值——
  这个项目里的碰撞，正是"把维度当成了同一件事"的典型后果。
  把这次的经验迁移到数据建模里，就是一个很实在的面试案例。

# 05 · 组织数据范围与跨模块数据归属

> 对应代码：`party-org`（OrgService / RosterService / OrgLevelProviderImpl）、
> `party-content`（ResourceService / ResourceValidator / ResourceAuditHandler）、
> `party-boot`（DataScopeAspect）、`party-auth`（UserRosterProvider）
> 状态：✅ 完成，编译 BUILD SUCCESS

---

## 一、这个模块解决什么问题

「谁能看谁的数据」——这是任何 To B 系统都绕不开的问题，也是最容易出安全事故的地方。

这个项目的约束是：**管理员只能看本组织及下辖组织的数据**。组织是三层树
（党委 → 党总支 → 党支部），一个县党委管理员要能看到下面所有支部，一个村支书只能看自己支部。

难点在于「及下辖」这三个字：**怎么高效地表达「某节点及其整棵子树」**，
以及**在哪些地方必须显式处理「什么都看不到」这种边界**。

**一句话**：数据范围做对不难，难的是把所有边界都想全——漏一个就是一个越权漏洞。

## 三、关键决策与取舍

### 决策 1：数据范围的三种语义必须严格区分

这是本篇最重要的一条。`resolveVisibleOrgIds` 的返回值有三种含义：

| 返回 | 含义 | 行为 |
|---|---|---|
| `null` | 不限范围（平台管理员） | 不加组织条件 |
| 空列表 | **无任何可见组织** | 必须返回空结果 |
| 非空列表 | 具体范围 | `org_id IN (...)` |

**最容易犯的错**是这么写：

```java
if (visible != null && !visible.isEmpty()) {
    wrapper.in(AuditLog::getOrgId, visible);   // ❌ 空集时什么条件都不加
}
```

当 `visible` 是空列表时，这段代码**不加任何组织条件** → 查询退化成全表扫描
→ **用户看到了所有组织的数据**。

**正确写法必须给空集生成恒假条件**：

```java
if (visible == null) return;                 // 不限范围
if (visible.isEmpty()) {
    wrapper.eq(AuditLog::getId, -1L);        // 恒假
    return;
}
wrapper.in(AuditLog::getOrgId, visible);
```

我在 `AuditServiceImpl`、`AdminApplyServiceImpl`、`RosterServiceImpl` 三处都做了同样处理，
并在每处都写了对应的单测。**这种漏洞的可怕之处在于：它只在「用户不属于任何组织」时触发，
日常测试根本发现不了。**

### 决策 2：指定的组织越界时要明确拒绝，不能返回空列表

```java
List<Long> intersected = subtree.stream().filter(visible::contains).toList();
if (intersected.isEmpty()) {
    throw new BizException(ErrorCode.FORBIDDEN);   // 而不是 return List.of()
}
```

**为什么不能返回空列表**：
- 返回空列表，调用方会理解为「这个组织确实没有数据」——**把一次越权尝试伪装成了正常结果**
- 明确的 `3001 无权限` 才能被监控告警捕捉到，也才能让攻击者知道这条路走不通

> 这是安全设计的一个通用原则：**「无权限」和「无数据」必须是两种不同的响应。**
> 混在一起的直接后果是日志里看不出攻击行为。

### 决策 3：组织树用路径枚举，代价说清楚

```sql
path VARCHAR(255)   -- 形如 /1/12/35/
SELECT id FROM t_org WHERE path LIKE CONCAT(#{path}, '%')
```

**被否决**：`parent_id` 递归查询（`WITH RECURSIVE`）。

**代价（要主动讲）**：组织移动时要**重写整棵子树的 path**。这是写放大。
换来的是所有读路径都是 O(1) 索引查询——**读多写少的场景这笔账是划算的**。

**一个容易忽略的正确性细节**：路径必须带**尾斜杠**，否则
`"/1/120/".startsWith("/1/12/")` 会是 `true`，把兄弟节点误判成子孙。
尾斜杠不是装饰，是正确性的一部分（`OrgPathUtilTest` 里专门验了这条）。

### 决策 4：跨模块数据归属——名册拆成「数据」与「编排」两半

名册要展示党员信息（在 `t_user`，属 party-auth）+ 组织名称（在 `t_org`，属 party-org）。

**问题**：跨模块只允许调用对方的 service 接口，禁止直接读对方表。
但无论把 `RosterService` 放哪边，都会缺一半数据。

**解法**：**按职责拆，而不是按页面拆。**

```
party-auth  提供 UserRosterProvider（只读投影：谁、什么身份、什么民族、属于哪个组织）
party-org   负责编排：解析组织范围 → 调 provider 取数据 → 内存回填组织名 → 组装 VO
```

关键在于 `RosterRow` 是**只读投影 record，不是 auth 的实体**——
避免实体跨模块泄露（实体带着 setter 和数据库字段，泄露出去就等于把表结构交出去了）。

**组织名在内存里回填，而不是在 SQL 里 JOIN**：一次 `IN` 查询取回所有涉及的
组织名，然后在 Java 里 map。1000 人规模下多一次查询换掉跨模块 JOIN，是划算的。

### 决策 5：上架必须走审核流程，不能有旁路

```java
// changeStatus 里
if (target == ResourceStatus.PUBLISHED) {
    throw new BizException(ErrorCode.AUDIT_ILLEGAL_TRANSITION,
            "资源上架须通过审核流程，不能直接变更状态");
}
```

**为什么值得专门拦这一下**：我最初写的时候让 `changeStatus` 支持上架，
结果它会给审核流水写一条 `pending=1` 的记录——**管理员的待办队列里会多出一条
永远处理不掉的幻影任务**，而且内容实际上绕过了审核。

**修法**：上架只能通过 `AuditService.review`（它内部会清掉待审标记并写 APPROVE 流水）；
`changeStatus` 只负责下架与退回草稿这两个终结动作。

> 通用教训：**当一个状态有两个写入口时，一定要问「它们的副作用是否一致」。**
> 不一致就会产生脏数据。

### 决策 6：字段校验抽成纯函数

资源有复杂的跨字段规则（VR 不能有播放地址、视频必须有字幕、图文不能有字幕）。
这些规则我抽成了 `ResourceValidator.violations(...)`：

```java
public static List<String> violations(ResourceForm form, Integer vrTheme, Integer vrForm,
                                      String contentUrl, String subtitleUrl, Integer durationSec)
```

**两个设计点**：
1. **返回全部违规项而不是抛第一个错**——前端可以一次性提示所有问题，
   而不是让用户改一个报一个。
2. **纯静态函数，没有依赖**——单测不需要任何 mock，13 个用例跑完只要 0.03 秒。

**为什么不用注解做**：`@NotNull` 这类注解只能表达单字段约束，
「form=视频 时 subtitleUrl 必填」这种跨字段依赖注解表达不了。
硬用 `@AssertTrue` 写类级校验，会让规则散落且难以定位。

### 决策 7：数据范围切面放在 party-boot

`DataScopeAspect` 需要 `OrgService`，而 `OrgService` 在 party-org。

**如果切面放在 party-org**：其他模块要用它就得依赖 party-org，
而 party-learn、party-exam 本来就依赖 party-org，倒也没问题；
但如果放在某个业务模块里，就变成「一个业务模块承担了全项目的基础设施职责」，语义不对。

**放在 party-boot**：boot 是唯一依赖全部业务模块的装配层，
放这里既拿得到 `OrgService`，又不会产生任何循环依赖。

**顺带解决了一个细节**：加了 `scopeResolved` 标志位。

```java
if (context.isScopeResolved()) return;   // 一次请求内复用
```

**为什么不用 `visibleOrgIds == null` 判断**：「尚未解析」和「已解析但没有可见组织」
**都表现为空列表**，用列表是否为空来判断，会导致要么重复查库、
要么把空集当成未解析而放行——**又是一次越权**。

所以状态必须用独立标志位表达，不能从数据本身反推。
这个教训和前面的空集陷阱是同一类问题。

## 四、可迁移的方法论

1. **「无权限」和「无数据」必须是两种响应**，不能都返回空列表。
2. **空集永远要单独处理**——任何「条件为空则不加条件」的写法都是潜在越权。
3. **状态不要从数据反推**，用独立的标志位表达（已解析 / 未解析）。
4. **跨模块数据按职责拆，不按页面拆**；投影用 record，别传实体。
5. **一个状态有多个写入口时，逐个检查副作用是否一致。**
6. **跨字段校验规则抽成纯函数**：可测、可一次报全、无 mock。

## 五、面试考点清单

| # | 问题 | 答题要点 |
|---|---|---|
| 1 | 树形结构在 MySQL 里怎么存？四种方案怎么选？ | 邻接表（写简单读难）、路径枚举（读写均衡，适合读多写少）、闭包表（查询最灵活但表膨胀）、嵌套集（读极快写极慢）。**按读写比选** |
| 2 | 路径枚举的坑是什么？ | ① 节点移动要重写整棵子树 ② 前缀匹配必须带分隔符（尾斜杠），否则 `/1/120/` 会被误判为 `/1/12/` 的子节点 |
| 3 | 数据权限你觉得最容易出什么漏洞？ | 范围为空时忘记特判 → 条件不加 → 全表可见。还有「无权限」返回空列表掩盖越权尝试 |
| 4 | 怎么在代码里保证数据权限不被绕过？ | ① 范围解析只有一处实现 ② 用切面统一注入 ③ 关键查询写单测覆盖空集与越界两种边界 |
| 5 | 两个模块互相需要对方的数据，怎么拆？ | 按职责拆：数据的归属方提供只读投影接口，编排方负责组装。**不要让实体跨模块** |
| 6 | 为什么不在 SQL 里 JOIN 另一个模块的表？ | 破坏模块边界：对方改表结构你会被动崩掉。代价是多一次查询，在合理规模下可接受 |
| 7 | 跨字段校验用什么实现？ | 注解表达不了跨字段依赖。用纯函数收集全部违规项返回，既好测也能一次提示完 |
| 8 | 为什么校验要一次返回全部错误？ | 用户体验：改一个报一个会让人反复提交。这也是参数校验的通用做法 |
| 9 | 一个业务状态有两个写入口，你要检查什么？ | 每个入口的**副作用**是否一致：是否都写审计日志、是否都正确更新待办状态。不一致就会产生脏数据 |
| 10 | `ThreadLocal` 里存的对象，怎么判断「已初始化」？ | 不能用「值为 null」判断——初始值可能就是 null 或空集合。用独立布尔标志 |

## 六、可延伸的数据/算法点

- **组织树的路径枚举可以直接升级为图算法练习**：给定一组可见组织 id，
  求「最简覆盖集」（去掉被其他节点包含的子孙节点）。当前实现是把整棵子树查出来，
  当组织规模上千时，**先求最简覆盖集再查询**能显著减少 `IN` 列表长度。
- **名册的检索条件组合**（姓名 + 民族 + 身份类型）是一个典型的多维筛选问题。
  你选的「统计分析与 SQL 建模」方向可以从这里切入：用 `EXPLAIN` 观察
  不同条件组合下的索引选择，理解**复合索引的列顺序为什么必须匹配查询模式**——
  这是 SQL 调优里最实用的一块。
